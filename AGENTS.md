# Working on mikarevell.com

This is the portfolio site of the artist Mika Revell (Instagram: littlepinkpills). It is a static Astro site whose content lives in YAML and Markdown files in this repo, edited either by hand, by an agent, or through the TinaCMS editor at `/admin`. It deploys to Vercel. This file is the one place that explains how it all works and the rules for changing it; the README and CLAUDE.md point here.

The site should stay simple, fast and easy for Mika to add to. Nothing here needs to be clever.

## Set up a new machine

1. Install Node 24 (the version in `.nvmrc`; on a Mac with Homebrew, `brew install node@24`) and Google Chrome.
2. Clone the repo and run `npm ci`.
3. Install `gitleaks` (`brew install gitleaks`), which checks commits for secrets.
4. Get the secrets: `npm i -g vercel`, then `vercel login`, `vercel link --project mika-revell`, and `vercel env pull .env`. This needs a login with access to the Vercel project; ask Alex. The file holds the Blob upload token and the TinaCMS keys, and it is never committed.
5. Install the phone-browser engine for tests: `npx playwright install webkit`. If the download times out, see "Known quirks" below.
6. Run `npm run dev`. The site is at http://localhost:4321 and the editor at http://localhost:4321/admin/index.html.
7. Run `npm test` once to confirm everything passes before you change anything.

## How it fits together

- **Content** is in `src/content/`. Its shape is defined in `src/content/schemas.ts` and, for the editor, in `tina/config.ts`. The build fails if those two disagree (`scripts/check-schema.ts`).
- **Images** are stored in Vercel Blob, not in the repo. Content files hold the image URL. On the live site, Vercel resizes each image on request (`/_vercel/image`, set up in `src/lib/image.ts` and `astro.config.mjs`); locally the original file is shown. `src/data/image-dimensions.json` records each image's size so pages don't jump while loading. It is generated by `npm run images:dimensions`, which also runs on every build.
- **Pages** are in `src/pages/` and share `src/layouts/BaseLayout.astro`. Content lookups and link checking live in `src/lib/content.ts`.
- **Deploys**: every push to `master` is built and published by Vercel to www.mikarevell.com, usually within a minute. Pushes to other branches get a private preview URL. There is no other CI.
- **The editor**: TinaCMS at `/admin` saves each edit as a commit to `master` on GitHub (through Tina Cloud), which triggers a deploy. Locally, `npm run dev` runs the editor against the files on disk instead, and nothing is committed until you commit it.

## The content model

| Collection | Files | What it is |
|---|---|---|
| Artworks | `src/content/artworks/<id>.yaml` | One artwork: title, image URL, year, medium, dimensions, description. |
| Series (`works`) | `src/content/works/<id>.yaml` | A body of work with its statement, cover image and an ordered list of artworks. Its page is `/work/<id>/`. |
| Homepage | `src/content/homepage/featured.yaml` | The stack of images on the homepage, in order, each linking to a series and optionally an artwork. |
| About | `src/content/about/main.yaml` | Bio, two photos and the CV. |
| Contact | `src/content/contact/contact.yaml` | Photo and text beside the contact form. |
| Writing | `src/content/writing/<id>.md` | A page of writing: frontmatter plus Markdown text. Its page is `/writing/<id>/`. The Writing menu item appears only once one exists. |

Rules the code relies on:

- **The filename is the id and the URL.** `cruise-control.yaml` is the series at `/work/cruise-control/`, and it is what other files link to. Don't rename a file that other files link to without updating the links; the build will fail and name the broken link if you miss one.
- **Links between entries are repo paths**, for example `artwork: src/content/artworks/oil-spill.yaml` (with or without `.yaml`). A link to a missing entry, or a homepage link to a hidden series, fails the build.
- **Order** of artworks in a series and of homepage images is the order of the list. Order of series on `/work/` and of writing is the `order` number (lower first).
- **`hidden: true`** on a series or a piece of writing means it has no page and appears nowhere. New series made by the import script start hidden.
- `archive/` holds content kept for reference that the site and editor don't read, such as homepage images taken down for low resolution.

## Rules for every change

Every change to the site, code or content, goes through a GitHub issue. This applies to agents and people alike.

1. **Write the issue first**, using the "Site change" template in `.github/ISSUE_TEMPLATE/site-change.md`. It asks for the user need (as a user story), the part of the site, why, do's and don'ts, a plan, acceptance criteria and testing. The `write-site-issue` skill and `taste/issue-writing.md` hold the full guidance. Write in full sentences, with no em dashes.
2. **Write the plan in the issue before building.** If the plan changes while you work, update the issue and say what changed.
3. **Work on a branch**, not on `master`.
4. **Test on both a phone and a desktop view, every time.** `npm test` runs every check on desktop Chrome (1440px wide) and on an iPhone-sized Safari. Also open the changed pages yourself at both sizes in `npm run dev` and take screenshots for the issue.
5. **Run the checks and review the change** before asking for approval: `npm test`, `npm run build`, `npm run check` and `npm run check:secrets`, then the `review-change` skill (a code review plus this site's checklist). Post the results on the issue.
6. **Visual changes are reviewed, never accepted blindly.** The screenshot tests compare every page with the approved screenshots in `tests/e2e/__screenshots__/`. If a change is meant to alter how a page looks, open the diff images Playwright writes to `test-results/`, confirm the change is the intended one and nothing else moved, then run `npm run test:update-screenshots` and commit the new screenshots with the change. If a change is not meant to alter the look, a screenshot failure is a bug.
7. **Get approval.** Push the branch, which gives a Vercel preview URL. You can run the tests against it with `BASE_URL=<preview url> npm test`. Share the preview and screenshots with the person who asked, usually Mika or Alex, and wait for their approval.
8. **Deploy** by merging to `master`, then check the live site.
9. **Close the issue** only when the tests pass, the requester has approved, and the change is live. The closing comment says what shipped, the commit, what changed from the plan, and what is still open.

## Writing for the site

The words on the site are Mika's. Follow her voice, not a generic one.

- Mika's voice is written down in `taste/`, a taste package extracted from the site's own text (start with `taste/README.md`). Use the `write-in-mika-voice` skill to draft and `check-mika-text` to check. It has not yet been reviewed by Mika, so treat it as a guide, not a ruling.
- Never change the substance of Mika's own writing (bio, statements, series texts) without her approval. Propose changes in the issue. Clear typos and factual consistency fixes can go ahead but must be listed in the issue.
- Never invent facts about her work: titles, dates, venues, collaborators and mediums come from Mika.
- Plain writing rules apply to everything, including issues, docs and alt text: `taste/plain-writing.md`. In short: full sentences, no em dashes, no filler or marketing phrasing.
- Every image needs alt text. For artworks the title is used; for other images, describe what is shown.

## Common tasks

These have step-by-step skills in `.claude/skills/`, which any agent can follow.

- **Add a folder of new work** (a new series or more pieces in an existing one): `.claude/skills/add-work/SKILL.md`, built on `npm run images:import`.
- **Add a page of writing**: `.claude/skills/add-writing/SKILL.md`.
- **Make any other change** (the issue workflow above): `.claude/skills/site-change/SKILL.md`, with `review-change` for the review step.
- **Set up a new machine**: `.claude/skills/setup/SKILL.md`.
- **Reorder** artworks in a series or homepage images: reorder the list in the YAML file or drag in the editor. Series order on `/work/` is each series's `order` number.
- **Hide or show a series**: set or remove `hidden: true`.

## Secrets and security

- **Secrets live only in Vercel**, as environment variables on the `mika-revell` project: `BLOB_READ_WRITE_TOKEN` (image uploads), `TINA_CLIENT_ID`, `TINA_TOKEN` and `TINA_SEARCH_TOKEN` (the CMS). A machine gets them with `vercel env pull .env`, and `.env` is gitignored. To change one, change it in Vercel (`vercel env add` or the dashboard), then pull again. Never paste a secret into code, content, an issue or a commit.
- **Generated files that can contain secrets are not committed**: `tina/__generated__/` (its client embeds the Tina token) and `public/admin/` are rebuilt on every build.
- **GitHub checks every push**: secret scanning with push protection, Dependabot alerts and Dependabot security updates are on for the repo. `npm run check:secrets` runs the same kind of check locally on the branch's commits.
- **Known, accepted `npm audit` findings**: moderate advisories in `react-router` 6, used only inside the TinaCMS editor. They are fixed only in `react-router` 7, which TinaCMS doesn't support yet, and they don't affect the public site. `path-to-regexp` is pinned to a patched version through `overrides` in `package.json`.
- The contact form posts to Formspree; its form id in `src/pages/contact.astro` is public by design.

## Known quirks

- **Astro 7 moves `astro dev` to the background** when it detects an agent. The `dev` script passes `--ignore-lock` to keep it in the foreground, because the TinaCMS server stops when Astro's process exits. If you see "Dev server already running", run `npx astro dev stop`.
- **Playwright's browser download can time out** even when the network is fine. The desktop tests use the installed Google Chrome, so only WebKit is needed. If `npx playwright install webkit` fails, run `npx playwright install --dry-run webkit` to get the download URL and install location, download it with `curl -L`, unzip it into that location, and create empty `INSTALLATION_COMPLETE` and `DEPENDENCIES_VALIDATED` files there.
- **TinaCMS reads `.env`, not `.env.local`.** That is why setup pulls the secrets into `.env`.
- **Build speed**: a deploy takes about 50 seconds when Vercel's build cache is warm and about two and a half minutes without it (the first deploy after a long gap, or a manual redeploy without cache). Most of the extra time is installing dependencies. The TinaCMS editor build takes about 35 seconds of every deploy.
- **Image optimization is billed per image size requested.** Keep `IMAGE_WIDTHS` in `src/lib/image.ts` and `imagesConfig` in `astro.config.mjs` short and in step with each other.
